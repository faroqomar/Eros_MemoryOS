Mandatory architecture and ownership

Mandatory architecture, C34 (2026-11-14): use **MVVM (Model-View-ViewModel)** for SwiftUI features, with independent domain/use cases and thin replaceable adapters. Views render state and forward user actions; ViewModels own feature state and call injected use cases; domain models/rules stay independent of SwiftUI, storage implementations, and provider SDKs. Views and ViewModels must not call databases, network services, or engine SDKs directly. Keep view-local presentation state in Views; do not create empty ViewModels for stateless display components. Follow the [explicit MVVM, repository, and engine rules](docs/how-to/commercial-engineering-rules.md#mandatory-mvvm-repository-and-engine-rules). Step 1 must map actual files and dependencies to these roles. Step 2 must inspect code, trace actions, and test the boundaries; naming folders or classes is not evidence of compliance. This policy update does not certify the existing demo or start a refactor.

Keep the app local-first and use a modular monolith. Keep one private canonical MemoryOS app repository. “Separate engine repositories” means selected upstream library repositories/checkouts, not new custom memory/speech engines. Keep upstream source outside app source, pin reviewed versions, and integrate through small app-owned interfaces and thin adapters. Keep real core/integration targets in the app repository when SDK integration begins. Fork only for a justified required patch. Recording, transcription, retrieval, and model execution remain independently replaceable. Do not infer a provider selection, new repository, or integration from these rules.

Step 2 code and test review

C34 explicitly requires MVVM and the existing app/upstream ownership rules. The verifier must inspect actual source, record file/symbol evidence, and check each applicable item below. A folder name, class suffix, diagram, or statement that the rules were read cannot substitute for this review.

- **MVVM:** trace an affected user action from View to ViewModel to use case. Check that Views contain presentation and input forwarding, ViewModels own feature state and action coordination, and product rules live in the domain. View-local UI state and stateless display components remain valid; do not require empty ViewModels. - **Dependency direction:** inspect imports, constructors, and calls. Views/ViewModels must not call concrete databases, network clients, or engine SDKs. Domain code must build without SwiftUI/UIKit or provider/storage implementation dependencies. Verify initializer injection from the composition root and app-owned values across adapter APIs. - **Behavior tests:** check affected ViewModel state/action/error transitions and use-case rules through controlled dependencies, plus adapter contracts when affected. Test observable outcomes; file names or mirrored implementation assertions do not prove separation. - **Git repositories and engines:** verify one canonical app repository, upstream-owned engine source in its own checkout/package, justified forks, reviewed pinned revisions, and removal of delivery overrides. Confirm that no copied engine implementation, unnecessary custom engine repository, or unapproved provider selection entered the change. - **Replaceability and data:** inspect separate implemented recording/transcription/retrieval/model contracts, app-owned originals/IDs/corrections, and rebuildable provider indexes. Apply the existing contract, multilingual/offline, recovery/upgrade, and physical-device checks below when affected.
